适用 `http://127.0.0.1:18741` 的十一月工作台。活动数据目录为 `F:\2026年11月\作图\过程资料\november-workbench`；`F:\期刊AI工作台\work\november-workbench` 是指向它的 junction，不是另一份数据。恢复只用当前工作台、统一生产入口及实际任务记录，不覆盖反馈、验收、原稿、候选或历史。

## 先诊断，不要连续重启

```powershell
& 'F:\期刊AI工作台\repo\workbench\diagnose-november.ps1'
```

这是只读检查。`ready` 表示 `/data` 返回含 articles 和 rows 的有效响应；`starting_or_stalled` 表示检测到本工作台 Node 进程但端口未监听，既可能正在初始化也可能卡住，不能仅凭进程存活断定正常；`listening_not_ready` 表示端口已监听但数据接口不可用；`unavailable` 表示没有检测到就绪服务或对应进程。非 ready 返回退出码 2。若端口由不属于该工作台的进程占用，先核实进程，不停止或覆盖。

进程存在时记录 PID、创建时间、CPU、日志变化及检查时间，随后复查**同一 PID**和 `/data`；超时不是进程已退出的证据。生产任务仍运行时不热改共享引擎或盲目重启。若当前无服务进程和监听，使用已有计划任务启动一次：

```powershell
Get-ScheduledTask -TaskName NovemberFigureWorkbench
Start-ScheduledTask -TaskName NovemberFigureWorkbench
& 'F:\期刊AI工作台\repo\workbench\diagnose-november.ps1'
Get-Content 'F:\期刊AI工作台\work\november-workbench\login-start.log' -Tail 20
```

计划任务 `Running` 只代表任务在运行，不代表工作台已就绪；任务启动动作发现已有监听时会退出，不能当作重启。2026-11-04 实例：PID 2672 活着、端口拒绝连接，后来 `/data` 才返回285条；观察到启动消耗至少约100秒 CPU。初始化慢的具体函数尚未通过剖析证实，不把“恢复任务”或“哈希检查”当作已确认根因。三分钟生产计时包含等待工作台，不能从启动完成后重新计时。若服务长时间未就绪且 CPU、日志、进程状态均无进展，保存证据后再诊断；不因观察超时反复新建进程。

## 回传、预览、终审与恢复

- 已生成但网络断开/预览失败：先查当前 `/data`、本次 `delivery-pending.json`、任务 `state.json` 与统一回执。核对图件、完整图号、来源和 SHA，已有结果只续接核验/同一候选回放；不重渲染、不重复发布。见 `production-runner.md` 和 `production-observability.md`。
- 候选回传后重启消失：查候选文件、输出集合、版本、回执和终审状态。撤回通过并不等于删除候选；只有证据和当前版本匹配才可恢复显示，不能自动改为已通过。见 `production-admission.md`、`common-revision-candidates.md`。不要手改 `acceptance.json`、`feedback.json` 修复显示。
- 反馈/原稿/当前图或路线变更：旧任务作废，保留旧证据，重新读取版本与来源；不能以旧候选覆盖新批注或已终检成图。没终审批注也可以对未终检候选走统一制作侧更正入口，不伪造用户批注。
- 领取失败/锁存在：先查 PID、锁归属和当前任务状态；活进程不夺锁，状态不明不删锁。不同图独立输出目录；工作台状态经统一入口写入。
- 普通 PDF 返回路径/封装错误：以服务端指定暂存位置和 `production-runner.mjs` 接续；先查已有 imported-pdf 及 attempt，匹配完整来源和哈希时接续，不手写 contract 或目标路径。修订和普通新图不要混用封装。
- 引擎签名/版本不一致：查机器配置、报告签名、当前 Python 和字体配置；不能自动接受未知签名、用旧引擎或把候选当当前版本。生产有活动任务时不热更；有确认的代码更新结束后按统一版本流程维护锁和故障登记。独立 Python/CLI 的代码下次调用加载，服务端代码变更才可能需要重启。
- 输入路径/参数错误、格式能力缺口、真实缺源、质量检查失败分开记录；不把操作错误计作工具能力失败，不把 EMF/WMF 解析失败自动当缺源。源和图意有冲突才挂该图，其他图继续。

## 启动耗时待修：线索与验证要求

2026-11-04 工作台含285条记录、231个输出；启动恢复记录中41条 commonCandidate 符合恢复条件，另6条属于旧反馈候选恢复。当前 `/data` 实测两次约2.23秒和1.82秒。源码中恢复过程中可多次调用 `refresh()`，而状态刷新逐项核验候选文件 SHA。这说明重复全量刷新是值得测量的线索，**不是已通过逐阶段计时确认的根因**。

下一次安排修复时，应在隔离数据副本逐阶段记录启动时间、恢复次数、哈希读取数和最终 `/data` 就绪时间，再用真实恢复场景核对候选、反馈、验收及完整输出SHA；不得通过跳过校验、提前报告ready或覆盖历史来换取启动速度。避免为了单次CLI修补反复重启工作台。
